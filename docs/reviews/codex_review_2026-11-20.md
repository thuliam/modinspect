- เปิด `/` และ `/price` ผ่านเซิร์ฟเวอร์ PHP ที่ใช้ `.env.testing` ได้: หน้า `/price` แสดง 41 รุ่นและ 0 รุ่นที่มีช่วงราคา จึงไม่ถือว่าราคาว่างเป็นบั๊ก การ์ดที่มีราคา กราฟ ผลดีลที่มีราคา และข้อมูลความเชื่อมั่นประเมินจาก view และโค้ด/เทสต์ ไม่ใช่ภาพหน้าจอที่มีข้อมูลจริง

- `/deal-checker/result/{uuid}`, `/read-listing` หลังส่งฟอร์ม, `/compare`, `/upgrade`, `/watching`, `/build`, `/condition-guide`, `/blog`, `/glossary`, `/methodology` และหน้ารายละเอียดที่มีราคาไม่ได้ตรวจแบบ interactive ครบทุกสถานะ ข้อค้นพบด้านล่างอาศัยไฟล์ที่ระบุ; ไม่ได้รันชุดเทสต์เต็มเพื่อหลีกเลี่ยงผลเขียนอื่นนอกไฟล์รายงาน ผลเทสต์จึงไม่ใช่ผลรันครั้งนี้

## 4. รายละเอียดทีละข้อ

### F01 — คะแนนค่าพลังและการแนะนำสเปก

- **หลักฐาน (ข้อเท็จจริง):** `/build` ใน `app/Views/modules/build.php:25,88-92` ระบุ “ค่าพลัง” และมีปุ่ม “แนะนำสเปกให้”; `app/Views/components/build-summary.php:53-57` แสดงคะแนนพร้อมกราฟ และ `app/Services/Build/BuildStats.php:18,77-89` คำนวณคะแนนเทียบสเปกสูงสุดในฐานและถ่วงน้ำหนัก ไม่ใช่ผลทดสอบจริง
- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** คะแนนและคำแนะนำสื่อการตัดสินความสามารถ แม้มีคำกำกับ ก็ขัดหลักที่กำหนดว่าแสดงข้อเท็จจริงโดยไม่มีข้อมูลประสิทธิภาพ
- **วิธีแก้ที่ทำได้เลย:** ใน `app/Views/modules/build.php` ซ่อนส่วน preset และปุ่มแนะนำ รวมทั้งนำข้อความค่าพลังออก; ใน `app/Views/components/build-summary.php` ซ่อนส่วนคะแนนและกราฟ ให้เหลือรายการชิ้นส่วน ราคาแยกฐาน และผลตรวจเงื่อนไขที่มีข้อมูลจริง ตรวจเส้นทาง `recommend` ฝั่ง controller ไม่ให้เรียกจากหน้าโดยตรงจนกว่าจะปรับให้สอดคล้องหลักนี้
- **วิธีตรวจว่าแก้แล้ว:** เปิด `/build` เลือกชิ้นส่วนและโหลดผลบันทึก ตรวจว่าไม่มีคะแนน แกนประสิทธิภาพ หรือปุ่มแนะนำ และยังเห็นสเปก ราคา และข้อจำกัดความเข้ากันได้; เพิ่มเทสต์ view และ request สำหรับ action เดิม
- **ความเสี่ยง/ผลข้างเคียง:** ความสามารถเดิมหายจาก UI ต้องตรวจลิงก์ผลบันทึกและ preview; ไม่เปลี่ยนราคาหรือสร้างข้อมูลประสิทธิภาพ

### F02 — ความยินยอมชวนเข้าใจว่าปรับราคาจากผู้ใช้

- **หลักฐาน (ข้อเท็จจริง):** `app/Views/deal/form.php:75-77` เขียนว่า “ยินยอมให้นำข้อมูลที่ไม่ระบุตัวตนไปปรับปรุงดัชนีราคา”; `app/Controllers/DealCheckerController.php:24-29` รับค่า consent และ `app/Models/DealCheck.php:14` บันทึกลง deal check หลักฐานนี้เพียงอย่างเดียวไม่ได้พิสูจน์ว่าระบบนำข้อมูลไปคำนวณ snapshot
- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** คนอ่านอาจเชื่อว่าราคาที่กรอกจะกำหนดดัชนีโดยตรง ซึ่งขัดหลักแยกสัญญาณจากราคาที่ตรวจแล้ว
- **วิธีแก้ที่ทำได้เลย:** ใน `app/Views/deal/form.php` ซ่อนช่องยินยอมนี้ชั่วคราวจนตรวจการใช้ข้อมูลครบ แล้วค่อยแสดงถ้อยคำตามการใช้งานจริง เช่น “หากยินยอม เราอาจใช้ข้อมูลที่ไม่ระบุตัวตนเพื่อศึกษาการใช้งาน ข้อมูลนี้ไม่กำหนดราคาตลาดโดยตรง” เฉพาะเมื่อยืนยันว่าตรงกับการใช้งานและการเก็บจริง
- **วิธีตรวจว่าแก้แล้ว:** ตรวจฟอร์มและการบันทึกทั้งเลือก/ไม่เลือก; ตรวจ pipeline และเทสต์ว่า deal check ไม่สร้าง observation หรือ snapshot โดยตรง และข้อความตรงกับนโยบายจริง
- **ความเสี่ยง/ผลข้างเคียง:** การซ่อนช่องเปลี่ยนการเก็บ consent ในอนาคต ต้องตรวจผู้ใช้ข้อมูลปลายทางก่อนเปลี่ยน ไม่ลบข้อมูลเดิม

- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** ผู้ใช้ใหม่อาจมองว่ารุ่นเหล่านี้ผ่านการจัดอันดับความคุ้มหรือประสิทธิภาพ ทั้งที่หลักฐานไม่ได้รองรับ
- **วิธีแก้ที่ทำได้เลย:** แก้ `home/index.php` เป็น “ค้นหา • เทียบ • ตรวจสอบที่มา • ประกอบการตัดสินใจ” และ “ตัวอย่างรุ่นในระบบ”; แก้ `build.php` เป็น “รุ่นที่มีราคามือสองก่อน” โดยคงลำดับเดิม

- **ความเสี่ยง/ผลข้างเคียง:** กระทบข้อความและเทสต์ที่อ้างข้อความเดิมเท่านั้น ไม่จัดอันดับใหม่

- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** ตัวอย่างชื่อรุ่นอาจอ่านยากบนจอเล็กหรือในที่สว่าง โดยเฉพาะผู้มีสายตาเลือนราง
- **วิธีแก้ที่ทำได้เลย:** ปรับ token สี placeholder ที่เกี่ยวข้องใน `public/assets/mi-theme.css` เป็นสีเข้มที่ทดสอบบนพื้นจริงได้อย่างน้อย 4.5:1 เช่น `#666666` บนขาวประมาณ 5.74:1 โดยใช้ token เดิมถ้ามีสีที่ผ่านอยู่แล้ว
- **วิธีตรวจว่าแก้แล้ว:** วัด computed color และพื้นจริงของ placeholder ที่ `/` ทั้ง 375px และ 768px รวมสถานะ focus; ตรวจ label ยังแสดงต่อ screen reader
- **ความเสี่ยง/ผลข้างเคียง:** กฎ CSS อื่นอาจ override หรือใช้พื้นต่างกัน ต้องวัดสีที่ render จริงก่อนยืนยัน

### F07 — ผลตรวจ bulk alias ใช้รหัสที่ผู้ดูแลต้องแปลเอง

- **หลักฐาน (ข้อเท็จจริง):** `app/Views/admin/aliases.php:27-36` ให้กรอก `product-slug` และแสดง `unknown_product`, `duplicate_in_file`, `conflict` พร้อมปุ่ม Check only/Import โดยไม่มีคำอธิบายความหมายหรือวิธีแก้ข้างผล
- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** ผู้ดูแลต้องเดาว่าบรรทัดใดควรแก้หรือหา slug จากไหน ทำให้นำเข้าซ้ำและตรวจทานช้าลง
- **วิธีแก้ที่ทำได้เลย:** เพิ่มคำอธิบายสั้นใน `app/Views/admin/aliases.php` เช่น “ไม่พบรหัสสินค้า — ตรวจ slug จากหน้าสินค้า” และ “ชื่อซ้ำกับสินค้าอื่น — ตรวจรุ่นก่อนนำเข้า” โดยคงรหัสสถานะภายในและขั้น Check only/Import เดิม ใช้ `small` และ Bootstrap `alert` ที่มีอยู่
- **วิธีตรวจว่าแก้แล้ว:** ใช้ข้อมูลทดสอบใน `tests/alias_import_test.php` ตรวจ new, exists, conflict, unknown และ duplicate ว่ามีคำอธิบายตรงสถานะและไม่ import บรรทัดที่ไม่ควร
- **ความเสี่ยง/ผลข้างเคียง:** อย่าเปลี่ยนกฎ resolver หรือบอกให้แก้ conflict โดยอัตโนมัติ; ต้องตรวจผลจริงในหน้า admin ที่ล็อกอิน

### F08 — โหลด assets เฉพาะงานในทุกหน้า

- **หลักฐาน (ข้อเท็จจริง):** `app/Views/layouts/header.php:60-61` โหลด Select2 CSS ทุกหน้า; `app/Views/layouts/footer.php:51-54` โหลด Select2, ภาษาไทย, ตัวเชื่อม และ `spec-builder.js` ทุกหน้า ไฟล์ในเครื่อง `select2.min.js` 70,851 bytes, CSS 14,966 bytes และ `spec-builder.js` 12,224 bytes เป็นขนาดไฟล์ดิบ ไม่ใช่ขนาดส่งจริง
- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** หน้าอย่าง methodology อาจจ่ายค่า request และ parse สำหรับฟังก์ชันที่ไม่ได้ใช้ โดยเฉพาะเครือข่ายมือถือ ผลกระทบจริงยังไม่ได้วัด
- **วิธีแก้ที่ทำได้เลย:** ตรวจการใช้ Select2 และ spec-builder ในทุก view ก่อนกำหนดรายการ asset ตามหน้าที่ต้องใช้ใน `header.php`/`footer.php`; ใช้ไฟล์ bundled เดิม ไม่ดาวน์โหลดไลบรารี
- **วิธีตรวจว่าแก้แล้ว:** เปรียบเทียบ Network แบบปิด cache ที่ `/methodology`, `/price`, `/compare`, `/build` วัดจำนวน request, transferred bytes และทดสอบ dropdown/การเลือกชิ้นส่วนครบ
- **ความเสี่ยง/ผลข้างเคียง:** บาง component ร่วมอาจพึ่ง Select2 โดยไม่เห็นจากชื่อหน้า ต้องตรวจ dependency และลำดับโหลดก่อนตัดสินใจ

### F09 — คำรับรองความเข้ากันได้กว้างเกินกฎที่ตรวจ

- **หลักฐาน (ข้อเท็จจริง):** `app/Views/modules/build.php:25` เขียนว่า “ระบบกรองให้เหลือเฉพาะรุ่นที่ใช้ด้วยกันได้”; `app/Services/Build/BuildPreview.php:72-80` มีสถานะ unknown/warn และ `app/Views/components/build-summary.php:68-71` มีสถานะ “ตรวจไม่ได้”
- **ทำไมเป็นปัญหาต่อผู้ใช้ (ความเห็น):** ผู้ใช้อาจเข้าใจว่าเครื่องที่เลือกตรวจครบและประกอบได้แน่นอน แม้บางเงื่อนไขไม่มีข้อมูล
- **วิธีแก้ที่ทำได้เลย:** เปลี่ยน lead ใน `app/Views/modules/build.php` เป็น “ระบบช่วยตรวจเงื่อนไขที่มีข้อมูล บางรายการอาจตรวจไม่ได้ โปรดตรวจสเปกและขนาดจริงก่อนซื้อ” และคงสถานะผ่าน/ไม่ผ่าน/ตรวจไม่ได้
- **วิธีตรวจว่าแก้แล้ว:** เลือกชุดที่มีข้อมูลขาดใน fixture แล้วตรวจว่าข้อความและสถานะ unknown แสดงพร้อมกันทั้ง preview และผลบันทึก
- **ความเสี่ยง/ผลข้างเคียง:** ต้องไม่เปลี่ยนกฎ compatibility หรือแปลง unknown เป็นผ่าน

## 5. ข้อเสนอฟีเจอร์

1. **รายการตรวจสภาพแบบสั้นก่อนนัดรับ:** ผู้ใช้ต้องจำสิ่งที่ต้องถามหลายข้อ; ใช้ข้อความและหมวดที่มีใน `app/Views/modules/condition-guide.php` เป็นลิงก์/รายการสรุป ไม่ต้องใช้ข้อมูลใหม่; ค่าใช้จ่ายภายนอก 0 บาท; ขนาด S; เป็นรายการตรวจข้อเท็จจริง ไม่จัดอันดับรุ่น และควรตรวจว่าซ้ำกับ checklist ในผลดีลก่อนทำ
2. **ทางไปดูรุ่นที่ติดตามจากหน้าสินค้า:** ผู้ใช้ที่กดติดตามอาจหากลับไม่เจอ; ใช้รายการติดตามในเบราว์เซอร์และ route `/watching` ที่มีอยู่ (`app/Views/pages/watching.php:7-11`); ค่าใช้จ่ายภายนอก 0 บาท; ขนาด S; แสดงรายการที่ผู้ใช้เลือกเอง ไม่จัดอันดับหรือทำนายราคา ตรวจตำแหน่งลิงก์ที่มีอยู่ก่อนเพิ่ม
