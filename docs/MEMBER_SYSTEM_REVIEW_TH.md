# ทบทวนระบบสมาชิก (ผู้ซื้อและผู้ขาย) — 2026-11-24

อ่านและตรวจอย่างเดียว ยังไม่แก้โค้ดของระบบสมาชิก แผนหลักที่มีอยู่แล้ว: `docs/marketplace/REQUIREMENTS_INTAKE_PLAN_TH.md` และ `IMPLEMENTATION_GAP_ANALYSIS_TH.md` เอกสารนี้ยืนยันสถานะจริงตอนนี้และเสนอลำดับถัดไป

## 1. สถานะจริง (ตรวจจากโค้ดและ DB ที่ใช้อยู่ ณ วันนี้)

| ส่วน | มีในโค้ด | เปิดใช้จริง |
|---|---|---|
| สมาชิก (members, member_identities) | OAuth Google/Microsoft/Facebook, `/account` (โปรไฟล์, ความชอบ, ลบบัญชี, คำขอความเป็นส่วนตัว, ยอมรับข้อกำหนดแบบมีเวอร์ชัน) | **ยังไม่มีสมาชิกเลย (0 แถว)** ไม่มี client id/secret ของทั้ง 3 เจ้า (HG-13) หน้า `/account/login` เปิดได้แต่ล็อกอินไม่ได้ |
| สิทธิ์ (capability) | `MemberCapabilities` มีค่า `seller` ให้สมาชิกถือได้หลายสิทธิ์ (คนเดียวเป็นทั้ง buyer และ seller ได้) แอดมินเป็นคนให้ มีบันทึกตรวจสอบ | ยังไม่มีใครได้สิทธิ์ |
| ผู้ซื้อ (buyer) | ไม่มีสิทธิ์แยก ถือว่าสมาชิกทุกคนเป็น buyer โดยปริยาย มีแค่ชุดประกอบที่ผูก `member_id` และรายการติดตามที่เป็นคุกกี้ (ไม่ผูกสมาชิก) | — |
| ผู้ขาย (seller) | `seller_listings` + รูป (re-encode ลบ EXIF เก็บนอก web root), `/seller/*`, ส่งประกาศเข้าคิวแอดมิน, หน้า `/listings/{uuid}` | ปิด (`SELLER_LISTINGS_PUBLIC=false`) มีประกาศ 0 รายการ `/seller` redirect ไปล็อกอิน |
| เช็กผู้ขาย (blacklist) | `seller_reports` + หลักฐาน + ข้อโต้แย้ง | ปิด (`SELLER_CHECK_ENABLED=false`) รอทนาย (HG-14) และคีย์ HMAC (HG-18) |
| ข้อกำหนด/ความเป็นส่วนตัว | ตาราง `legal_documents`, `legal_acceptances`, `privacy_requests` มีแล้ว | ไม่มีเนื้อหาข้อกำหนดในตาราง (0 แถว) เนื้อหาต้องผ่านทนาย |
| แอดมิน | แยกจากสมาชิกชัดเจน (RBAC) | ยังไม่มี MFA ของแอดมิน |

## 2. สิ่งที่ขาดสำหรับ "buyer + seller ใช้งานได้จริง"

**ผู้ซื้อ**
1. รายการติดตามผูกกับบัญชี (ตอนนี้เป็นคุกกี้ เปลี่ยนเครื่องแล้วหาย) ต้องมีตาราง `watch_items` ผูกสมาชิก และรวมกับ push (ตาราง `push_subscriptions` ที่ทำไว้แล้วเก็บรายการติดตามอยู่แล้ว ผูก `member_id` ได้ภายหลัง)
2. บันทึกประกาศ/การค้นหา (saved listings, saved searches)
3. ค้นหาและกรองประกาศ, รายงานประกาศที่น่าสงสัย
4. โควตา Free ฝั่งเซิร์ฟเวอร์ (ตัวเลขในแผนเป็นสมมติฐาน ยังไม่ใช่ข้อเท็จจริง)
5. การแจ้งเตือน: ตอนนี้มีแค่ push (ปิดอยู่) ยังไม่มีอีเมล (ต้องไม่เสียเงิน)

**ผู้ขาย**
1. โปรไฟล์ผู้ขายและการยืนยันตัวตนโดย moderator (`seller_profiles`, `seller_verification_events`) — ตอนนี้ได้สิทธิ์ `seller` ครั้งเดียวจบ ไม่มีสถานะยืนยัน
2. ประกาศ: จำนวนสินค้า, วันหมดอายุ, สถานะ reserved/sold, ประวัติสถานะ (`listing_status_events`)
3. กติการาคา: ประกาศที่อนุมัติ **ไม่นับ** เป็นหลักฐานราคาตลาด (HG-17 ค่าเริ่มต้น) ต้องคงไว้และมีเทสต์ lineage
4. คิวตรวจรวมของ moderator (ประกาศ, ชุมชน, รายงาน)
5. ห้ามเก็บเบอร์/ชื่อจริง/ที่อยู่จริงของผู้ขายตามกฎ PII ของโปรเจกต์ การติดต่อผ่านตัวกลาง (ข้อความในระบบ) เป็น P2

**ร่วม**
- การเข้าสู่ระบบ: แผนเดิมถามว่า OAuth อย่างเดียวหรือเพิ่มอีเมล+รหัสผ่าน (D1) ค่าเริ่มต้นที่เสนอ: OAuth + ลิงก์ยืนยันทางอีเมลแบบบันทึก log เท่านั้นตอนพัฒนา
- ก่อนเปิดจริง: MFA แอดมิน, ข้อกำหนดและนโยบายความเป็นส่วนตัวผ่านทนาย, ใส่คีย์ OAuth, TLS/HSTS

## 3. ข้อจำกัดที่ต้องรู้ก่อนเริ่ม
- **DB ของเว็บจริงกับ DEV เป็นชุดเดียวกัน** (เซิร์ฟเวอร์เดียวกัน) ทุก migration ของสมาชิกจึงมีผลกับเว็บจริงทันที ต้องเป็น additive และปิดสวิตช์ไว้เสมอ
- เลข migration ถัดไปคือ `037` (แผนเดิมเขียน 031 ซึ่งถูกใช้ไปแล้ว)
- ห้ามดาวน์โหลดไลบรารีเพิ่มโดยไม่ขออนุมัติ; ค่าใช้จ่าย 0 บาท (ไม่มีอีเมลเสียเงิน, ไม่มี payment จริง)
- ระบบ OAuth เขียนเองด้วย curl ของ PHP อยู่แล้ว (ไม่มีไลบรารี)

## 4. ลำดับที่เสนอ (ต่อจาก LS-86)

| LS | งาน | ต้องการจากพี่ |
|---|---|---|
| **LS-87** | ผู้ซื้อ: ตาราง `watch_items`, รายการติดตามผูกบัญชีเมื่อล็อกอิน (ไม่ล็อกอินยังใช้คุกกี้เหมือนเดิม), เชื่อม push เข้ากับสมาชิก, โควตา Free ฝั่งเซิร์ฟเวอร์ | ยืนยันตัวเลขโควตา (watch 3 รุ่น?) |
| **LS-88** | ผู้ขาย: `seller_profiles` + `seller_verification_events` (moderator ยืนยันเอง), ประกาศเพิ่ม quantity/expiry/reserved/sold + `listing_status_events` | ยืนยันว่า HG-17 คงเดิม (ประกาศไม่นับเป็นหลักฐานราคา) |
| **LS-89** | ค้นหา/กรองประกาศ, saved listings/searches, รายงานประกาศ, คิว moderation รวม | — |
| **LS-90** | ความปลอดภัยก่อนเปิดจริง: MFA แอดมิน (TOTP), ซ้อมเปิด-ปิดสวิตช์ ตรวจ PII | อนุมัติไลบรารี TOTP หรือให้เขียนเอง (RFC 6238 สั้นและทดสอบด้วยเวกเตอร์มาตรฐานได้) |
| **LS-91** | การแจ้งเตือนสำหรับสมาชิกแบบ log-only (คิวแจ้งเตือน) | — |

**งานที่ต้องเป็นพี่ (ผมทำแทนไม่ได้):** สร้าง OAuth app ของ Google/Microsoft/Facebook แล้วใส่คีย์ใน `.env` (HG-13), ให้ทนายอ่านข้อกำหนด/PDPA (HG-14), สร้างคีย์ HMAC (HG-18), ตัดสินเรื่องเปิดประกาศสาธารณะ (HG-16)

**สิ่งที่ยังไม่ได้ตรวจ:** การล็อกอิน OAuth จริง (ไม่มีคีย์), หน้าตาของ `/account/login` และ `/seller` ตอนล็อกอินแล้ว (ไม่มีสมาชิกทดสอบ), เทสต์ฝั่งสมาชิกทั้งชุดบน DB ทดสอบ
