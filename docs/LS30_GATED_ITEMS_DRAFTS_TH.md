# LS-30 B: ร่างสำหรับเรื่องที่รอการตัดสินใจ (ร่างทั้งหมด ยังไม่ประกาศใช้)

ข้อมูลในเอกสารนี้ตรวจจากโค้ดและ migration 022–028 ณ 2026-11-21 ไม่ใช่คำแนะนำทางกฎหมาย ต้องให้ทนายและเจ้าของตัดสินก่อนใช้จริง ฟีเจอร์ community, seller check และ sign-in ยังปิดอยู่ด้วย env flag จนกว่าเจ้าของสั่งเปิด

## 1. รายการข้อมูลที่ระบบเก็บจริง (ใช้ตรวจร่างนโยบายความเป็นส่วนตัว HG-14)

ร่างเดิม `PRIVACY_TERMS_DRAFT_TH.md` เขียนก่อนมีสมาชิก ฟอรัม ประกาศขาย และผลหลังซื้อ จึงขาดตารางด้านล่างนี้ ทนายควรเทียบตารางนี้กับร่างทีละแถว

| ตาราง | เก็บอะไร | ข้อมูลระบุตัวตน | ใครเห็น | ตั้งต้นคิดเรื่อง retention |
|---|---|---|---|---|
| `deal_checks` | ราคาที่ผู้ใช้กรอก สภาพ ผลที่แสดง uuid | ไม่มีชื่อ/เบอร์ (consent เป็นแค่ธง) | คนถือ uuid | ตามค่า `--deal-checks-days` |
| `deal_outcomes` (028) | ซื้อ/ต่อรอง/ไม่ซื้อ และราคาจ่ายจริง ไม่มีข้อความอิสระ | ไม่มี | แอดมิน (สรุปรวม) | หายพร้อม `deal_checks` (ON DELETE CASCADE) |
| `spec_builds` | สเปกที่จัดชุด `member_id` ถ้าล็อกอิน | ผูกกับสมาชิกเมื่อมี | เจ้าของชุด | `--builds-days` |
| `members` (023) | ชื่อที่แสดง อีเมล เวลายอมรับข้อกำหนด เข้าใช้ล่าสุด สถานะ | อีเมล ชื่อ | แอดมินที่มีสิทธิ์ | จนกว่าสมาชิกลบบัญชี (`/account/delete`) |
| `member_identities` | ผู้ให้บริการ + รหัส subject + อีเมล | รหัสบัญชีภายนอก | ไม่แสดงสาธารณะ | ลบพร้อมสมาชิก (CASCADE) |
| `seller_listings` + `seller_listing_photos` (024) | ประกาศขายของสมาชิก รูป | รูปสินค้า (ยังไม่ได้ตรวจว่ามีกติกาห้ามรูปบุคคลหรือที่อยู่ ควรให้เจ้าของกำหนด) | สาธารณะเมื่อเผยแพร่ | ตามสถานะประกาศ |
| `seller_reports` + evidence + disputes (025) | ตัวระบุผู้ขายที่ถูกรายงาน (ชนิด เบอร์โทรหรือบัญชีธนาคาร; วิธีเก็บให้ตรวจ ADR-007 และโค้ดก่อนเขียนลงนโยบาย) หลักฐาน คำโต้แย้ง | ข้อมูลของบุคคลที่สาม ความเสี่ยงสูงสุด | แอดมิน | `--seller-pending-days` ลบเฉพาะ pending/rejected |
| `community_reports` (026) | รายงานข้อมูลราคาผิด | ไม่ควรมี | แอดมิน | `--community-days` ลบเฉพาะ rejected/spam |
| `community_threads/posts/reviews/votes/flags` (027) | กระทู้ ตอบ รีวิว โหวต ธงรายงาน | ข้อความที่สมาชิกพิมพ์เอง ผูกกับสมาชิก | สาธารณะเมื่อ visible | `--forum-days` ลบเฉพาะที่ถูกซ่อน |

คำถามที่ทนายต้องตอบ (ไม่ใช่ให้ผมตอบ):
1. ฐานทางกฎหมายสำหรับข้อมูลบุคคลที่สามใน `seller_reports` (เบอร์/บัญชี) ใช้ประโยชน์โดยชอบด้วยกฎหมายได้หรือไม่ และต้องแจ้งผู้ถูกรายงานอย่างไร
2. ข้อความยอมรับก่อนสมัคร/ก่อนโพสต์ ต้องมีอะไรบ้าง และเก็บหลักฐานการยอมรับ (`terms_accepted_at`) พอหรือไม่
3. การลบบัญชีควรลบเนื้อหาในฟอรัมด้วย หรือทำให้ไม่ระบุตัวตน (ตอนนี้ `MemberAuth::deleteAccount` ตัด `member_id` ออกจาก `spec_builds` แล้วลบแถว `members` ส่วนเนื้อหาฟอรัมและประกาศขึ้นกับ FK ของตารางนั้น ต้องตรวจก่อนสรุปกับทนาย)
4. การตรวจคำต้องห้าม (ชื่อ เบอร์ ไลน์ไอดี คำกล่าวหา) ใน `ContentGuard` เพียงพอเป็น "มาตรการสมควร" หรือไม่

## 2. ข้อเสนอ retention (ตัวเลขเป็นข้อเสนอ ไม่ใช่ค่าที่ตั้งไว้)

เครื่องมือ `cli/retention_purge.php` ไม่มีค่าเริ่มต้น ไม่ลบอะไรถ้าไม่ระบุจำนวนวัน ทำงานแบบ dry run เว้นแต่ใส่ `--apply` ขั้นต่ำ 7 วัน

| ข้อมูล | ข้อเสนอ | เหตุผล |
|---|---|---|
| `deal_checks` (และผลหลังซื้อ) | 180 วัน | ใช้ดูผลย้อนหลังได้ครึ่งปี และตัวเลขสรุปไม่ต้องใช้แถวดิบ |
| `spec_builds` ของผู้ไม่ล็อกอิน | 90 วัน | ไม่มีเจ้าของให้กลับมาแก้ |
| รายงานชุมชนที่ rejected/spam | 90 วัน | ตรงกับ ADR-006 |
| รายงานผู้ขาย pending/rejected | 60 วัน | ข้อมูลบุคคลที่สาม ควรสั้นที่สุด (verified/disputed ไม่แตะ) |
| เนื้อหาฟอรัมที่ถูกซ่อน | 90 วัน | เก็บไว้พอให้ตรวจสอบการตัดสินของผู้ดูแล |
| rate-limit | 24 ชั่วโมง | ไม่มีเหตุต้องเก็บนาน |
| สมาชิกที่ไม่ใช้งาน | ยังไม่มีเครื่องมือ | ต้องให้เจ้าของ/ทนายกำหนดเกณฑ์ก่อน แล้วค่อยเสนอสร้างเครื่องมือ |

คำสั่ง dry run (ปลอดภัย ไม่ลบอะไร) และคำสั่งจริงแยกบรรทัด:

```powershell
php cli/retention_purge.php --deal-checks-days=180 --builds-days=90 --community-days=90 --seller-pending-days=60 --forum-days=90 --ratelimit-hours=24
```

```powershell
php cli/db_backup.php
```

```powershell
php cli/retention_purge.php --deal-checks-days=180 --builds-days=90 --community-days=90 --seller-pending-days=60 --forum-days=90 --ratelimit-hours=24 --apply
```

สามบรรทัดนี้ผมไม่ได้รัน `--apply` บน DEV รันแค่ dry run เมื่อเจ้าของสั่ง

## 3. คู่มือผู้ดูแลชุมชน (moderator)

หลักการที่โค้ดบังคับอยู่แล้ว:
- ธงจากสมาชิก 3 คนที่ต่างกัน ซ่อนเนื้อหาทันทีและส่งเข้าคิว (`Forum::FLAGS_TO_HIDE = 3`) คนตัดสินคือผู้ดูแล ไม่ใช่ระบบ
- การตัดสินทุกครั้งบันทึกใน audit พร้อมตัวตนผู้ดูแล

ขั้นตอนประจำวัน (หน้า `/admin/community-moderation`):
1. เปิดคิว อ่านข้อความเต็มของรายการที่ถูกธง
2. ตัดสิน: **uphold** = ซ่อนต่อ, **dismiss** = แสดงกลับและปิดธง, **hide/restore** = ซ่อน/คืนตรงๆ, **lock/unlock** = ล็อกกระทู้ไม่ให้ตอบ
3. เนื้อหาที่ต้องซ่อนเสมอ: ชื่อจริงหรือเบอร์ของบุคคล, ไลน์ไอดี, การกล่าวหาว่าโกงโดยไม่มีหลักฐาน, โฆษณา, ข้อมูลส่วนตัวของผู้อื่น
4. เนื้อหาที่ควรคงไว้: ประสบการณ์ตรงที่ไม่ระบุตัวบุคคล ("การ์ดเสียภายในสองวัน")

รายงานผู้ขาย (`/admin/seller-reports`, ปิดอยู่ HG-14/HG-18):
1. อ่านหลักฐานและสถานะ (pending, verified, rejected, disputed)
2. ถ้าผู้ถูกรายงานโต้แย้ง สถานะเป็น disputed และห้ามเผยแพร่ผลจนกว่าจะปิดข้อโต้แย้ง
3. ถ้าหลักฐานไม่พอ ให้ rejected (จะถูกลบตาม retention)

สิ่งที่ผู้ดูแลต้องไม่ทำ: ตัดสินโดยไม่อ่านข้อความเต็ม, ส่งสกรีนช็อตของรายงานให้ผู้อื่น, แก้ราคาตลาดจากสัญญาณชุมชน (สัญญาณชุมชนไม่เคยตั้งราคา)

ต้องให้เจ้าของตัดสินก่อนมีผู้ดูแลจริง: ใครเป็นผู้ดูแล, เวลาตอบสนองที่สัญญา, ช่องทางที่ผู้ถูกรายงานโต้แย้ง

## 4. รายการตรวจ OAuth (HG-13)

Redirect URI ที่ต้องลงทะเบียนที่ผู้ให้บริการแต่ละราย (`APP_URL` คือโดเมนจริงตอน deploy):

- `{APP_URL}/account/callback/google`
- `{APP_URL}/account/callback/microsoft`
- `{APP_URL}/account/callback/facebook`

| ผู้ให้บริการ | ค่าที่ต้องได้ | ตัวแปร env | หมายเหตุ |
|---|---|---|---|
| Google | Client ID, Client Secret | `MEMBER_GOOGLE_CLIENT_ID`, `MEMBER_GOOGLE_CLIENT_SECRET` | OIDC scope `openid email profile` |
| Microsoft | Application (client) ID, Secret | `MEMBER_MICROSOFT_CLIENT_ID`, `MEMBER_MICROSOFT_CLIENT_SECRET` | ลงทะเบียนแบบรองรับบัญชีส่วนตัว (Hotmail/Outlook) |
| Facebook | App ID, App Secret | `MEMBER_FACEBOOK_APP_ID`, `MEMBER_FACEBOOK_APP_SECRET`, `MEMBER_FACEBOOK_GRAPH_VERSION` | scope `public_profile,email`; ต้องผ่านการตรวจแอปหากเปิดให้คนทั่วไป (ตรวจเงื่อนไขล่าสุดกับ Facebook เอง) |
| Apple | ไม่ให้บริการ | - | ต้องจ่ายค่าสมาชิกนักพัฒนา (HG-15) ขัดนโยบายไม่มีค่าใช้จ่าย |

ก่อนเปิด:
1. ทุกผู้ให้บริการที่ลงทะเบียนต้องไม่เรียกเก็บเงินหรือขอบัตรเครดิต ถ้าต้อง ให้หยุดและแจ้ง OWNER_APPROVAL_REQUIRED
2. ลิงก์นโยบายความเป็นส่วนตัวและข้อกำหนดที่หน้าลงทะเบียนของผู้ให้บริการ ต้องมาจากข้อความที่ทนายอนุมัติแล้ว (ข้อ 1)
3. เก็บ secret ไว้ใน `.env` บนเซิร์ฟเวอร์เท่านั้น ห้ามอยู่ใน git ห้ามส่งในแชต แล้วรัน `php cli/predeploy_report.php` ให้ผ่านโดยไม่มีคำเตือนเรื่อง secret
4. ทดสอบด้วยบัญชีทดสอบของเจ้าของเอง ล็อกอิน ออก ลบบัญชี แล้วตรวจว่า `members` และ `member_identities` หายครบ
5. ค่าเริ่มต้น: เว้นว่างทุกตัว = ปิดการล็อกอิน

## สิ่งที่ผมไม่ได้ทำ

ไม่ได้เปิดฟีเจอร์ใด ไม่ได้ลบข้อมูลบน DEV ไม่ได้ติดต่อผู้ให้บริการ OAuth ไม่ได้ประกาศข้อความใดบนเว็บ
